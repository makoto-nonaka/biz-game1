# SmartApps Biz Game v0.5 — 高校生向けアプリ経営ゲーム

高校1年生20〜30人、50分の授業向けです。開始時に設定した1〜4ラウンドで市場選択・稼ぎ方・投資回収・競争を体験します。改訂バランスW1に、市場別の開発資源・生産性向上・移行費用を追加しています。

## v0.5 試行バランス（2026年10月26日）

課金率30％、広告収入300円、基本運営費30万円。Freeの獲得力を補い、Freemiumへの価格の影響をPaidより穏やかにしました。詳細・再現手順・限界は [v0.5検証結果](docs/BALANCE-v0.5.md)。3・6・10・15社で検証しています。
更新後は必ず `/admin.html?new=1` から新しいゲームを作成してください。画面上部に「バランス v0.5」と表示されます。既存のゲームはv0.4以前の設定を維持します。下記の過去版の説明は改訂履歴です。

## 管理者の解説と記録出力

集計後、管理者画面の「各ラウンドの差がついたポイント」に当回利益を比較した解説を表示します。最新回は開いた状態、過去の回は折りたたみ表示です。利益差の内訳と、選択を1項目だけ比較相手と同じにした計算を確認できます。モデル・価格は整合を保つため一組として変更します。生成AIや外部サービスは使いません。
「分析用の記録を保存」からCSV・テキストを保存できます。選択、OS別利用者数、収入・費用・利益、当回・累計順位、開発資源、解説と比較計算、計算ルールを記録します。集計前は確定状況と提出済みの選択を保存し、未確定の選択・未集計の結果は空欄です。管理者の権限をAPI側でも確認し、プレイヤーには非公開です。
詳細は [解説と出力の使い方](docs/ADMIN-ANALYSIS.md)。今回の追加でv0.5のパラメーターや保存形式は変更しません。既存ゲームにそのまま使用できます。

## 起動

Node.js 22以上、追加ライブラリ不要です。解凍したフォルダで実行します。

```sh
zsh ./起動.command
```

このMacではCodex同梱Node.jsを自動検出します。他のPCでは通常のNode.jsを用意してください。`node server.js` または `npm start` でも起動できます。

ゲーム運営管理者は <http://localhost:3000/admin.html>、プレイヤーは <http://localhost:3000/> または <http://localhost:3000/student.html> を開きます。HTMLファイルのダブルクリックではなく、起動したサーバーのURLで開いてください。別ゲームが3000番を使っている場合：

```sh
PORT=3001 zsh ./起動.command
```

この場合はゲーム運営管理者が <http://localhost:3001/admin.html>、プレイヤーが <http://localhost:3001/> を開きます。起動中はターミナルを開いたままにし、停止はControl+Cです。

## 遊び方

1. 運営管理者が `admin.html` でゲームを作成し、**3桁の参加コード（100〜999）**をプレイヤーに伝えます。
2. プレイヤーは入口でコードと会社名を登録。Android／iOSへの配分、Free／Freemium／Paid、価格、開発・広告を選び確定します。
3. 全社が確定したら、運営管理者が集計。各端末の画面は約3秒で更新されます。
4. 利益・収入内訳・順位・他社の選択を比較して振り返ります。
5. 運営管理者が次へ進め、設定した最終ラウンドの集計で終了です。

1台で試すには、運営管理者タブを残して別タブの入口からプレイヤーを登録します。追加のプレイヤーも入口から別会社名で登録できます。再接続は「参加中の会社に戻る」を使い、二重登録を避けてください。端末内に運営管理者・プレイヤーの操作権限を保存します。ブラウザデータの削除や別端末への権限復旧は未実装です。

同じWi-Fiのスマホでは `http://MacのローカルIP:3000` を開きます。`localhost` はスマホ自身を指します。学校Wi-Fiが端末間通信を制限している場合はクラウド配信を利用してください。

## v0.4の変更

- 開発資源が市場別に蓄積し、次回以降の開発生産性と既存品質に少し寄与。資源は各回80%残存。
- 大きな市場変更には移行費用（全振りの反転で20万円）。確定前・結果・損益に反映。
- 広告は当回のみ有効。
- ゲーム運営管理者は `admin.html`、プレイヤーは `index.html`／`student.html` に入口を分離。
- プレイヤー画面からルール本文・リンクを削除。生産性の内部指標はプレイヤーに表示しない。
- 運営管理者画面に未確定・確定済みの会社名と人数を分けて表示。

詳細と比較試算は [開発資源・生産性の設計](docs/RESOURCES-v0.4.md)。`npm run simulate:resources` で再実行できます。

## 基礎となるv0.3の変更

- 参加コードを3桁に変更。保存先内で重複させず発行します。全900個使用済みならメッセージを返し、待ち続けません。
- Freeは仮想的な半年で1人400円の広告収入。
- Freemiumは課金40%＋広告付き無料60%。500円課金なら1人あたり売上440円。
- 低価格・バランス・品質の3種類の顧客を各OSに配置。
- 開発・広告の追加50万円による効果を逓減。市場集中の追加効果も逓減。
- 確定前に人数を仮定した利益例と分岐点を表示。参入する市場の全員を得ても黒字にならない条件は明示。
- 結果で販売・課金収入、受取広告収入、支払広告投資を区別。各社の顧客タイプ別人数も閲覧可能。

**新版では新しいゲームを作成して試してください。** 既存の保存ゲームは旧ルールのまま継続し、過去の結果を再計算しません。従来の6桁コードは既存ゲームへの再接続用に保持します。新版ZIPには保存データ・権限情報を含めません。

## 配置方法

### A. Renderだけで配信（最初におすすめ）

1. このフォルダの内容をGitHubのリポジトリへ登録します。`data/` と `.env` は含めません。
2. Renderでそのリポジトリから **Blueprint** を作成し、`render.yaml` を読み込みます。
3. `npm start` で画面とAPIを同じURLから配信します。公開されたURLを全員で開きます。
4. この設定は **starterプランと1GBの永続ディスクを使う有料構成** です。作成前にRenderの料金表示を確認してください。

通常のWeb Serviceとして設定する場合も、Build Command `npm install --omit=dev`、Start Command `npm start`、Health Check `/api/health`、`DATA_DIR=/var/data/startup-lab`、ディスクのマウント先 `/var/data` を指定します。PORTはRenderの指定を使います。

保存にJSONファイルを使うため、**サーバーは1プロセス・1インスタンス**で動かしてください。Renderの永続ディスクは有料サービス向けです。ディスクなしの一時ファイル構成では再起動・再配置でデータが失われるため授業用には使いません。詳細は [Render Web Services](https://render.com/docs/web-services)、[Persistent Disks](https://render.com/docs/disks) を参照してください。

### B. Vercelで画面、RenderでAPI

1. まずAのRenderサーバーを作成します。
2. Vercelで同じGitHubリポジトリをインポート。Framework Presetは **Other**。`vercel.json` にBuild Command `npm run build` とOutput Directory `dist` を設定済みです。
3. Vercelの環境変数に `API_BASE_URL=https://実際のAPI名.onrender.com` を設定して配置します。ビルド時に画面の接続先を生成します。
4. Renderの `ALLOWED_ORIGINS` に実際のVercel公開オリジン（例 `https://実際のプロジェクト名.vercel.app`）を設定して再配置します。末尾 `/` は付けません。複数ならカンマ区切りです。
5. VercelのURLで作成・参加・集計まで確認します。APIと画面のURLを変更したら、両方の設定を更新します。Preview URLを使うときも、そのURLを明示的に許可します。

Vercel単体でJSON保存する構成にはしていません。継続する授業データはRender側の永続ディスクに置きます。Vercelの出力設定は [公式設定資料](https://vercel.com/docs/project-configuration/vercel-json) を参照してください。クラウドへの実際の配置は今回行っていません。

### 環境変数

| 変数 | 初期値 | 用途 |
| --- | --- | --- |
| `PORT` | `3000` | サーバー待受ポート |
| `HOST` | `0.0.0.0` | サーバー待受アドレス |
| `DATA_DIR` | プロジェクト内 `data` | 保存先。クラウドでは永続ディスク上を指定 |
| `ALLOWED_ORIGINS` | 空 | 別サイトの画面を許可するURL。カンマ区切り |
| `API_BASE_URL` | 空 | 静的画面ビルド時のAPI URL |

`.env.example` は説明用です。`.env` の自動読込は行いません。ローカルで変更する例：`PORT=3001 npm start`。

## 保存と運用上の範囲

データは `data/games.json` に保存します。一時ファイルの書き込み後に置き換え、保存成功時だけ操作を反映します。壊れたデータがあれば空データで上書きせず起動を止めます。授業後に残す場合はサーバーを停止して保存フォルダをバックアップしてください。

操作権限にはランダムな秘密トークンを使います。参加コードだけでは運営管理者操作や他社の確定はできません。端末内とサーバー保存ファイルには操作権限が含まれるため、共有PCでは扱いに注意してください。公開後もゲームの新規作成は誰でも可能な試作用設計です。不特定多数向けの常設公開をする場合の作成制限・監視・保存期限は今後の課題です。

## ランキングと公開情報（2026年10月26日更新）

結果画面の「累計利益／売上／利用者数／モデル別」で表示を切り替えます。
累計利益は全ラウンドの合計です。売上・利用者数・モデル別は対象ラウンドを選択できます。
利用者数は合計・Android・iOSを切り替えます。モデル別はFreeの選択企業、Freemiumの課金価格、Paidの販売価格を表示し、価格はモデル内の高い順（同額は同順位）です。価格は経営の優劣を表しません。
他社の売上は学習用の比較指標として公開します。投資額、費用、市場配分、損益分岐点、生産性の内部指標は引き続き非公開です。自社の詳細と運営管理者用の全社詳細は確認できます。
新規追加の `public/rankings.js` もアップロードしてください。管理者・プレイヤーの内部権限名と既存の入口URLは互換性のため従来のままです。

## ラウンド回数とグラフ

管理画面でゲーム作成時に1〜4ラウンドを選べます（初期値3）。作成後は変更できません。設定のない既存ゲームは3回を維持します。

意思決定画面では、現在の選択で売上と費用の直線を描き、その交点を損益分岐点として表示します。開発・広告投資、市場配分による移行費用、価格、収益モデルを変えると更新します。横軸は利用者数、縦軸は金額。交点を読めるよう表示範囲を調整し、実際の市場上限は別記します。人数の予測ではありません。

結果発表時は管理者・プレイヤー双方に累計利益の横棒グラフを表示します。全社で共通目盛り、降順で、黒字は中央のゼロ線より右に緑、赤字は左に赤を表示します。会社名と金額は文字でも読み取れます。集計済みの過去ラウンドがある場合、次回意思決定中も直近までの累計を表示します。

CSV/TXTにも設定ラウンド数を記録します。計算モデルv0.5の収入単価・顧客配分・費用は変更していません。グラフに外部サービスや追加ライブラリは必要ありません。

## 1人用のコンピュータ対戦

起動後に `/singleplay.html` を開きます。通常のプレイヤー入口にもリンクがあります。会社名、コンピュータ企業2〜14社（初期値5社）、ラウンド数1〜4回（初期値3回）を選んで開始します。意思決定を確定すると自動で集計され、結果とグラフが表示されます。「次へ」で自分のペースで進めます。参加コードと管理者の操作は不要です。

同じ端末・ブラウザから途中再開できます。参加情報は `singleplay` キーに保存され、通常ゲームの `student` / `teacher` キーとは分かれています。`/singleplay.html?new=1` で新規対戦の準備画面を表示します。新しい対戦を開始すると、そのブラウザでの再開先は新しい対戦になります。

コンピュータは6種類の方針（Freeの集客型・費用抑制型、Freemiumのバランス型・高価格型、Paidの品質型・低価格型）を繰り返し割り当てます。市場配分には対戦ごとの小さな違いを加えます。赤字なら開発・広告費を段階的に減らし、課金・販売型で利用者が少なければ価格も下げます。一部企業は前回の市場別利用者数から配分を10ポイント調整します。収益モデル自体は維持します。最適戦略を探索するAIではなく、練習用のルールに従う相手です。

相手の選択は各ラウンド開始時に保存されます。プレイヤーの今回の選択はコンピュータ判断の入力に含みません。第2回以降は過去の結果を使います。集計では通常ゲームと同じv0.5モデルを使い、開発経験の蓄積・市場移行費用も計算します。

1人用のゲームは3桁の参加コード枠を使わず、専用の内部IDで保存します。他のプレイヤーの途中参加はできません。プレイヤーには通常と同じ範囲の公開情報のみを返し、コンピュータの非公開投資・費用・内部資源は開示しません。外部AI・追加ライブラリ・追加環境変数は不要です。

`singleplay.html` は既存のサーバーを使う画面です。HTMLファイルの直接ダブルクリックではなく、起動済みサーバーまたは公開済みサイトのURLから利用してください。

## チームの複数端末参加

新しい管理画面では参加枠を1〜30チーム分発行し、共通の参加QRコードと6桁のチームキーで受付します。キーは大小文字を区別しません。チーム名・代表者の選択を全メンバーに共有し、代表者だけが確定できます。受付締切時に実際に参加したチームだけで市場規模を確定します。未参加枠を手動削除する必要はありません。

運用方法・代表者切替・既存ゲームとの互換性は [docs/TEAMS.md](docs/TEAMS.md) を参照してください。QR生成ライブラリのライセンスは [docs/THIRD_PARTY.md](docs/THIRD_PARTY.md) にあります。
